# Markdown Editor — Project Kickoff

I want to build a lightweight desktop markdown writing app for my own personal use. This is not a portfolio piece — prioritize working, maintainable code over impressive architecture. Fast startup and low memory footprint over feature breadth.

The live preview's job is to represent what the PDF export will look like — treat it as a print preview, not a small interactive webpage. Let that guide inclusion calls throughout: web-navigation affordances (clickable heading permalinks, hover-revealed UI) and reader conveniences for a hosted page (copy-to-clipboard buttons) don't fit here, since I'm the author and the real source is already sitting in the adjacent editor pane.

## Stack

- **Tauri v2** (Rust backend + native OS webview — WebView2 on Windows, WebKit on macOS/Linux)
- **Frontend:** vanilla HTML/CSS/JS. No React/Vue/framework. Use a minimal bundler (Vite) only if needed to pull in npm packages like CodeMirror — dev-time tooling only, doesn't add runtime weight.
- **Markdown parsing:** `markdown-it` with `html: true`, `linkify: true`, `typographer: true` (matches my site's config) plus `markdown-it-footnote` and `markdown-it-deflist`. Reuse the `table_open`/`table_close` renderer override that wraps tables in a `.table-wrapper` div — the CSS already expects this.
- **Code syntax highlighting:** `highlight.js`, wired via markdown-it's `highlight` option — this is what my site actually uses. Do NOT use starry-night or anything targeting the `.pl-*` class scheme; those classes in `markdown-styles.css` are unused leftovers (likely from a `github-markdown-css` template) and can be deleted. Write a dedicated set of `.hljs-*` rules with their own new custom properties — roughly 12-14 variables (keyword, string, comment, number, function/title, class/type, attribute, built-in, literal, regex, variable, punctuation) gives good differentiation without exceeding 20. Do not reuse `--color-accent` or any other existing UI variable for these — they should be fully dedicated to syntax highlighting. Note: the code-block background is currently a single fixed dark hue in both light and dark app themes (not tied to a light/dark-swappable variable) — as long as that stays true, these new token colors only need to be defined once, not once per theme. If the code-block background ever becomes theme-aware, the token colors need to follow suit.
- **Mermaid diagrams:** `mermaid` npm package. Detect fenced code blocks tagged `mermaid` and swap in a `.mermaid` div with the raw diagram text for Mermaid to render — no code-details/toggle wrapper (see feature 5). Initialize Mermaid's theme based on the app's current light/dark state, not hardcoded — my site hardcodes `theme: 'dark'`, which would fight the theme toggle here. Debounce live-preview re-rendering (roughly 150–300ms after typing pauses) rather than re-running Mermaid on every keystroke; diagram layout is expensive enough to cause visible lag otherwise.
- **Math rendering:** KaTeX, not MathJax — dramatically lighter and faster (synchronous rendering vs. MathJax's heavier async pipeline), which fits the lightweight/fast priority. Use its `auto-render` extension to scan rendered HTML for `$...$`/`$$...$$` delimiters — a direct replacement for the `MathJax.typeset()` pass in my reference script. Run it on the same debounced re-render cycle as Mermaid, not on every keystroke. Trade-off: KaTeX covers the large standard/AMS-math LaTeX subset, not 100% of LaTeX — fine for typical logic/algebra notation (`\mathbb`, `\mathfrak`, `\vdash`, `\models`, aligned/cases/matrix environments are all supported), but if an exotic macro comes up that it doesn't recognize, MathJax is the fallback with broader coverage at higher cost.
- **Editor component:** CodeMirror 6 with `@codemirror/lang-markdown` for syntax highlighting in the editing pane.
- **Spell check:** try native `spellcheck` on CodeMirror's editable DOM first (WebView2 is real Chromium, so this should draw on the OS spell-check engine for free). Fall back to `nspell` or `typo-js` (pure JS, Hunspell-compatible) only if native spellcheck proves unreliable in the webview.
- **PDF export:** `window.print()` triggering the native print dialog, with `@media print` CSS rules to control margins. There is no built-in silent/programmatic PDF export API exposed to JS in WebView2 — this is the standard Tauri approach. See the print-handling note below for one required extra step. Considered and ruled out: Pandoc, Prince, WeasyPrint, wkhtmltopdf — none of these execute JavaScript, and both Mermaid and KaTeX require it to produce their output. Using any of them would mean pre-rendering those to static images with a headless browser first, which just duplicates the rendering engine already embedded via WebView2.

## Core features

1. **Split-pane layout** — markdown source editor (left) and live rendered preview (right), resizable divider, scroll position synced between the two.
2. **Multiple file tabs** — open and edit several files at once, switch between tabs, show an unsaved-changes indicator per tab, prompt before closing a tab with unsaved changes.
3. **Menu bar** with File menu: New, Open, Save, Save As, Export to PDF. Standard keyboard shortcuts (Ctrl+N, Ctrl+O, Ctrl+S, Ctrl+Shift+S, and a shortcut for export).
4. **Syntax highlighting** in the editor for markdown syntax — headers, bold/italic, code fences, links, blockquotes.
5. **Custom CSS preview** — the rendered preview uses my own stylesheet (attached: `markdown-styles.css`) as a starting template, not a source of truth — anything in it can change if it makes more sense for the app, including the language-label list, the theme-transition selector list, and the unscoped `path` rule. It's currently scoped to `.markdown-body`; that can be modified too.
   - **Heading anchors:** keep heading `id` attributes and the underlying `<a href="#id">` jump-links — Chromium's print-to-PDF preserves in-page anchor links as clickable internal jump-links within the exported PDF, so this has real value even in a static document. Drop only the decorative hover-reveal "#" icon UI (`.octicon-link`, the embedded octicons font-face, the hover-visibility behavior) — that part exists specifically so a website visitor can grab a shareable URL, which has no equivalent in a PDF. Note: this does NOT give a PDF reader's sidebar Bookmarks/Outline panel — Chromium's browser-based print-to-PDF doesn't generate that from HTML headings. A real outline would need either an experimental, uncertain-support WebView2 DevTools Protocol feature or post-processing the generated PDF with a library that injects an outline — treat as an optional future enhancement, not v1 scope.
   - Drop entirely: the mermaid "Code Details" toggle CSS (`code details`, `code details summary` and its hover state) — this app should not include the show-source-toggle feature at all. Also drop the whole "General Details: underline grow" block (`summary::after` and its hover/open triggers) — it's a hover animation, and hover states don't serve this app's preview-of-a-static-PDF purpose. Keep the separate marker-hiding rules (`summary::-webkit-details-marker`, `summary::marker`) — those are basic cross-browser normalization, not part of the animation, and still matter for a force-expanded `<details>` to look right.
   - Drop entirely: the `.pl-*` PrettyLights rules (see Stack note on highlight.js above), and the copy-to-clipboard button feature from the reference JS — a reading convenience for a hosted page, redundant when the source is already in the adjacent editor pane.
   The language-label list (`code.language-python::before` etc.) is a fixed set and will show raw `language-xxx` text for anything not listed (Rust, TOML, YAML, etc. — all realistic given this app's own stack). Extend it, or better, generate the label in JS at render time so adding a language doesn't require a CSS change.
6. **Spell check** — squiggly-underline misspelled words in the editor.
7. **Light/Dark theme switch** — the CSS's current three-block structure (`:root` default, a `prefers-color-scheme` media query fallback, and a `[data-theme]` override) is website-specific — it exists to give anonymous visitors a sensible default before any explicit choice is made. Since this is a standalone app, simplify: read the OS theme once at launch, explicitly set `data-theme="light"` or `"dark"` on the root element, and listen for OS theme changes to update it live. That collapses the three blocks into two explicit ones (light and dark) with nothing implicit left to keep in sync. The theme-transition selector list (`body, header, header h1, header a, article, article a, kbd`) is also copied from the website's DOM and doesn't cover any of the app's actual UI (tab bar, menu bar, editor surface, preview scroll container, split-pane resizer) — rewrite it for the app's real elements rather than extending it. If it makes sense, split the variable blocks and transition rules into their own `globals.css`/`variables.css` file — naming is up to you.
8. **Bold and Italic keybinds** — selecting text and using Ctrl+B/Ctrl+I should wrap (or strip, if already present) the selection (or the cursor position if nothing is selected) in the requisite number of `*`. Handle the nested case carefully — toggling italic on already-bold text (`**text**`) should produce `***text***`, not strip the bold.
9. **Preview pane context menu** — right-clicking text in the preview pane should add a "Jump to source" entry to the context menu (not replace the native menu) that snaps the editor cursor to the corresponding location. Build this on the same line-mapping mechanism as scroll sync (feature 1): configure markdown-it to stamp source line numbers onto rendered block elements (`data-source-line`, via markdown-it's `token.map`) and use that mapping for both scroll position and jump-to-source, rather than solving them separately.

## Print/PDF-specific handling

- Since PDF export is a static snapshot, any `<details>` block in the actual document content needs to be forced open before printing, or its content silently vanishes from the export. CSS can't toggle the `open` attribute — this needs a small JS step that sets `.open = true` on every `<details>` element right before `window.print()` fires.

## Suggested build order

1. Scaffold with `create-tauri-app` (vanilla JS template), confirm `cargo tauri dev` opens a blank window
2. Basic split pane: textarea + markdown-it rendering into a preview div, no styling yet
3. Wire in the actual CSS files, confirm the preview matches the site's rendering (minus the dropped anchor/copy-button/details-toggle features)
4. Add highlight.js + Mermaid rendering
5. Swap the plain textarea for CodeMirror 6 with markdown syntax highlighting
6. Scroll sync + jump-to-source, built on the shared line-mapping mechanism
7. Tabs (multi-file state, unsaved indicators)
8. Menu bar + keyboard shortcuts + file read/write via Tauri's fs API
9. PDF export via `window.print()` + print stylesheet, including the force-open-details step
10. Spell check
11. Polish pass
